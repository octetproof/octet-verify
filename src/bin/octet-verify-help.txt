octet-verify — independent verifier for Octet LocationProof artifacts

USAGE:
    octet-verify <proof.bin> [OPTIONS]
    cat proof.bin | octet-verify [OPTIONS]

    octet-verify fetch <proof-id> --backend <url> --token <bearer> [OPTIONS]
    octet-verify watch            --backend <url> --token <bearer> [OPTIONS]
    octet-verify range            --backend <url> --token <bearer> \
                                  --since <ts> --until <ts> [OPTIONS]

ARGUMENTS:
    <proof.bin>    Binary octet.navigate.LocationProof (or a
                   ContinuousProofEnvelope with --envelope). Reads stdin if
                   omitted.

OPTIONS:
    --hardware-pubkey <file>   P-256 attestation public key (raw SEC1 bytes or
                               hex). Required to verify stage signatures for iOS
                               proofs that carry no certificate; for Android the
                               key is taken from the embedded certificate chain
                               when this flag is absent. If the proof carries an
                               attested certificate_chain[0], a supplied key must
                               EQUAL it — a conflicting key is refused (verify
                               against the attested key by omitting this flag).
    --ed25519-pubkey <file>    Enrolled device-signer Ed25519 public key (raw 32
                               bytes or hex). Used to verify the transport
                               signature in --envelope mode.
    --envelope                 Treat the input as a ContinuousProofEnvelope
                               (proof bytes + Ed25519 transport signature)
                               instead of a bare LocationProof.
    --max-age-seconds <n>      Freshness window. Default: 300.
    --nullifier-store <file>   Newline-delimited hex file of seen nullifiers;
                               best-effort, single-process local replay check
                               (appends). NOT concurrency-safe and NOT the
                               authoritative defense — cross-proof uniqueness is
                               enforced server-side at ingest.
    --expect-region <id>       Assert the proof claims this region. Typed form
                               country:US / subdivision:US-CA / city:San Francisco
                               matches type and value; the bare form (US-CA) is a
                               country/subdivision ISO-code alias. FAILS (not
                               skipped) if the proof's region has no identifier to
                               match (earth/ellipse/h3/bbox) or no region at all.
    --expect-region-type <t>   Assert the claimed region is of this type: one of
                               earth, country, subdivision, city, ellipse, h3,
                               bbox. The positive counterpart to --expect-region —
                               use it to affirmatively accept a geometric or
                               earth-region proof. FAILS on a type mismatch or no
                               region.
    --expect-region-contains <lat>,<lon>
                               Assert the claimed region CONTAINS this point
                               (decimal degrees). Positively asserts a geometric
                               proof by location: earth (always), city (disc),
                               ellipse, and bbox are evaluated. FAILS for a named
                               country/subdivision (no geometry — use
                               --expect-region) and for h3 (needs an H3 library not
                               in this build; use --expect-region-type h3), and on
                               no region.
    --expect-query-region <spec>
                               Assert the proof's bound QUERIED region (semantic-
                               binding v3) equals this region, so its signed
                               location_verdict answers within(this region). Specs:
                               earth | country:AT | subdivision:US-NY |
                               disc:<lat>,<lon>,<radius_m> |
                               ellipse:<lat>,<lon>,<semi_major_m>,<semi_minor_m>,<heading_deg>.
                               FAILS if the proof binds no query (v2/v1, background,
                               or a city query) or a different region.
    --session-nonce <hex>      Assert the proof is bound to this per-login session
                               nonce (hex). Supply the nonce the relying party
                               issued at login; verification recomputes the
                               signed sessionBinding stage over it. Absent ⇒
                               session-binding is NOT-CHECKED; supplied but
                               unmatched or unbound ⇒ FAIL.
    --require-session-binding  Require the per-login session binding: FAIL (not
                               NOT-CHECKED) if the proof carries no matching
                               commitment — no --session-nonce given, or no
                               sessionBinding stage. Off by default. Use it when
                               verifying a stored/relayed proof you require bound.
    --require-schema-v2        Require schema-v2 binding material: a proof with no
                               semanticFields stage (and, in --envelope mode, an
                               envelope with no replay-control) FAILs instead of
                               reporting NOT-CHECKED. Off by default (back-compat:
                               older proofs still verify). Arm this in lockstep
                               with the ingest gate; it is instantly reversible.
    --require-attestation      Require hardware attestation to have affirmatively
                               verified: FAIL unless App Attest (iOS) or the
                               key-attestation chain (Android) passed. Closes the
                               gap where stripped evidence reports NOT-CHECKED and
                               the proof still passes. Off by default. On a build
                               without --features appattest (which can't verify
                               attestation) it always FAILs. iOS: pair it with
                               --app-attest-config — App Attest is the only iOS
                               hardware root, so without that config an iOS proof
                               can never satisfy this and will FAIL.
    --app-attest-config <file> Verify the proof's Apple App Attest evidence
                               offline against the expected app identity in this
                               TOML config ([app_attest] team_id / bundle_id /
                               environment). Requires a build with the
                               `appattest` feature; otherwise reported NOT-CHECKED.
    --app-attest-enrolment-bundle <file>
                               Recover the attested key from an out-of-band App
                               Attest enrolment bundle so an assertion-only proof
                               (one carrying no attestation object — the steady
                               state, since iOS emits the object only on a key's
                               first proof) reaches app-attest PASS via the
                               cached-key path instead of NOT-CHECKED. Accepts the
                               JSON (v:1) or proto DeviceAttestation form,
                               auto-detected. Requires --app-attest-config (the
                               source of the expected app identity) and the
                               `appattest` feature. A stateless CLI does not
                               enforce cross-proof assertion-counter monotonicity
                               (use the library + a persisted key for that).
    --android-app-identity <package>,<cert_sha256_hex>
                               Bind the Android key-attestation chain to a specific
                               app: its package name and the SHA-256 (64 hex chars)
                               of the signing certificate's DER
                               (attestationApplicationId). Without it the chain
                               attests only "some key from some app". Requires the
                               `appattest` feature.
    --skip-hardware-attestation
                               Scope an `appattest` build to core verification
                               only: skip the offline hardware-attestation layer
                               (App Attest, Android key-attestation chain, and the
                               field-2 device-key signature). Useful for triaging
                               a legacy or synthetic proof with no real chain.
    --integrity-decode-url <url>
                               Online Google Play Integrity (opt-in). Base URL of
                               the first-party decode endpoint (POST /v1/integrity/
                               decode). Given with --integrity-decode-token and
                               --integrity-package, the `play-integrity` check
                               decodes the proof's PI token and verifies it binds
                               to this proof (nonce + package), is fresh, and meets
                               MEETS_DEVICE_INTEGRITY. Requires a build with the
                               `playintegrity` feature; https:// (http:// LAN only).
    --integrity-decode-token <token>
                               The verifier's OWN decode-scoped service credential
                               (octet_svc_) for the decode endpoint — NOT a device
                               activation bearer.
    --integrity-package <pkg>  The Android package the PI token was minted for:
                               sent in the decode request and the accepted package
                               for the binding check.
    --integrity-max-age-seconds <n>
                               Freshness window for the PI token's timestamp.
                               Defaults to --max-age-seconds. (+60s forward skew.)
                               A FAIL rejects the proof; transient/auth failures are
                               NOT-CHECKED (never fail-open). Absent config ⇒
                               play-integrity NOT-CHECKED.
    --json                     Emit a machine-readable report.
    -h, --help                 Show this help.

BACKEND FETCH MODE (subcommands; requires a build with --features net):
    The fetch/watch/range subcommands pull proofs from the Octet proof
    ingestion API. The backend is UNTRUSTED: fetched bytes run through the exact
    same verification pipeline as a local file, and no backend-supplied field
    (created_at, platform, …) ever affects the verdict.

    fetch <proof-id>   Fetch and verify one proof by id.
    watch              Poll /v1/proofs/latest and verify each new proof as it
                       arrives. Runs until interrupted (Ctrl-C).
    range              Verify every proof in a time window; exits non-zero if
                       ANY proof fails (use for batch audit).

    --backend <url>        Backend base URL. https:// required; plain http:// is
                           allowed only for LAN dev (localhost, 127.*, 10.*,
                           192.168.*).
    --token <bearer>       Activation bearer; exchanged for a scoped
                           proof_upload_token via POST /v1/proofs/auth.
    --seen-store <file>    Newline-delimited "proof_id sha256" file. Persists
                           seen proof byte-hashes across runs so a re-fetched id
                           returning different bytes fails loud (refetch
                           consistency). Always deduped within a single run.
    --interval <seconds>   watch poll interval. Default: 5.
    --since <ts> / --until <ts>   range bounds (RFC 3339, e.g. 2026-06-01T00:00:00Z).
    --hardware-pubkey, --expect-region, --expect-region-type,
    --expect-region-contains, --expect-query-region, --session-nonce,
    --require-session-binding, --require-schema-v2, --require-attestation,
    --max-age-seconds,
    --json, --app-attest-config, --app-attest-enrolment-bundle,
    --android-app-identity, --skip-hardware-attestation,
    --integrity-decode-url / --integrity-decode-token / --integrity-package /
    --integrity-max-age-seconds all apply as above — a
    fetched Android proof carries its real attestation chain, so on an
    `appattest` build attestation-root runs in fetch mode too. Historical proofs
    are older than the default freshness window — pass a wide --max-age-seconds
    when auditing past ranges.

    With --json, each proof emits one report object per line (JSONL).

EXIT CODES:
    0    authentic — valid AND signatures cryptographically verified
    1    invalid — a check actively failed
    2    usage, IO, decode, or backend error
    3    inconclusive — structurally valid but signatures not verified
         (e.g. no hardware key); never collapses into 0
    For automation, exit 0 is a safe authenticity gate. For range/watch the code
    reflects the worst proof seen (any 1 → 1, else any 3 → 3, else 0).

WHAT THIS VERIFIES (v1):
    - stage attestation chain linkage and per-stage hardware (P-256) signatures
    - proofAssembly binding every prior stage signature
    - commitment / nullifier / ZK-bytes bound to their signed stage hashes
    - freshness and (optionally) cross-run replay
    - the Ed25519 transport signature, when an envelope + key are supplied

WHAT THIS DOES NOT VERIFY (reported as NOT-CHECKED, never as a pass):
    - that the hardware key is genuine device hardware: the Android certificate
      chain is NOT validated to Google's attestation root, and iOS App Attest
      is not checked. A passing stage chain proves the proof is internally
      consistent and signed by the key it carries — not that the key is real
      hardware. Use --ed25519-pubkey with --envelope for device-identity
      binding, or wait for a later build that validates attestation roots.
    - the spoofing verdict / confidence / level fields (bound via stage hashes
      that need internal serialization to re-derive)
    - the ZK proof (placeholder backend in current SDK builds)

This verifier reads proofs only. It contains none of the SDK's
proof-generation or spoof-detection logic. See VERIFICATION-SPEC.md.
