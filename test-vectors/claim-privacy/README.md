# Claim-privacy vectors (grid-snapped city, disc and box claims)

Cross-repo source of truth for how SDK 4.0.0 builds city, disc and box claims on
a fixed latitude/longitude grid instead of centring them on the device, and for
how a verifier tells the two apart (VERIFICATION-SPEC §2.1d).

`vectors.json` is generated by the SDK's generator and pinned byte for byte in
both SDK test suites. This copy has the generator's provenance fields (`spec`,
`issues`, `generator`) removed; every other key and value is unchanged. Every
position is synthetic, not anyone's location.

## Contents

- `constants`: the grid levels, the `ρ_L` table, the accuracy ladder, the city
  radius and name, and the vertical step.
- `claims[]`: an input (position, accuracy-area radius, optional disc query,
  altitude) and the claim the SDK builds from it: `claimed_region`, the exact
  bits of every float (`f64_bits_hex`), `grid_level`, `accuracy_bucket_m`, and
  `region_type` / `region_id_v2_hex`, the claim's v2 semantic-binding digest.
  `expected.claim: null` means the SDK makes no claim at that level.
- `classification[]`: claimed regions and their label, `SNAPPED`, `LEGACY` or
  `NOT_APPLICABLE`.

## What consumes this

The `src/verify.rs` unit test `claim_privacy_vectors`:

- classifies every `classification[]` entry and expects its label;
- expects every claim in `claims[]` to classify as SNAPPED, at the SDK's grid
  level for a disc, and to have the SDK's v2 region digest, so the semantic
  binding covers the snapped bytes unchanged;
- checks `constants` against the verifier's own tables.

Regenerating a vector means changing the contract: do it in lockstep with the
SDK, never to make one side go green.
