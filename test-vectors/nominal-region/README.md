# Field-20 `nominal_region` vectors (centre-less ellipse)

Cross-repo source of truth for the uncertainty's `nominal_region` (field 20)
from SDK 4.0.0: always an ellipse with no centre, so field 20 gives the shape of
the uncertainty and never the device's position (VERIFICATION-SPEC §2.1d). An
unset centre hashes as (0, 0) in `octet-uncertainty-binding-v1`, so the binding
is unchanged.

`vectors.json` is generated by the SDK's generator and pinned byte for byte in
both SDK test suites. This copy has the generator's provenance fields (`spec`,
`issues`, `generator`) removed; every other key and value is unchanged. Every
value is synthetic.

## Contents

- `accepted[]`: an uncertainty the SDK signs, with the ellipse digest input and
  digest, the binding preimage, and its SHA-256.
- `rejected[]`: `nominal_region` values the SDK refuses to sign: a centre (also
  one at 0, 0), an H3 set, a 3D box, and no region.

## What consumes this

The `src/uncertainty.rs` unit test `nominal_region_vectors`:

- rebuilds every accepted uncertainty and expects the SDK's ellipse digest,
  preimage and preimage hash, and that field 20 does not disclose the position;
- expects every rejected `nominal_region` to count as disclosing, which the
  `claim-privacy` check reports (WARN, or FAIL on a v4 proof or with
  `--require-private-claims`).

Regenerating a vector means changing the contract: do it in lockstep with the
SDK, never to make one side go green.
